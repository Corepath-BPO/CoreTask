# 0007. UUID v7 primary keys

- **Status:** Accepted
- **Date:** 2026-08-04

## Context

Primary keys appear in URLs, API responses and client caches. Two requirements
pull in opposite directions:

- **Not enumerable.** `/workspaces/41` invites `/workspaces/42`. Sequential ids
  turn a missing authorisation check into a data breach and leak business volume
  (how many customers signed up last month).
- **Index-friendly.** Random keys scatter B-tree inserts across the whole index,
  which hurts write throughput and cache hit rate — the classic UUID v4 problem.

## Decision

**UUID v7**, generated by Prisma (`@default(uuid(7))`), stored as PostgreSQL
`uuid`.

UUID v7 puts a 48-bit millisecond timestamp in the high bits, so values sort by
creation time. Inserts land at the right edge of the index like a sequence, while
the remaining 74 random bits keep them unguessable.

The one human-readable identifier is the ticket key (`CORE-1001`), which is
scoped to a workspace and therefore leaks nothing globally.

## Alternatives considered

**Auto-increment integers.** Smallest and fastest, but enumerable and
information-leaking. A public/internal id pair solves that at the cost of a
second unique index and a lookup on every request.

**UUID v4.** Unguessable but fully random. Insert locality is poor, the index
gets larger and less cacheable, and there is no natural creation ordering.

**UUID v7 generated in PostgreSQL.** A `uuid_generate_v7()` plpgsql function is a
well-known ten-line snippet, and keeps ids correct for rows created by raw SQL.
Rejected because it adds a hand-maintained database function to every
environment, and because generating client-side means the id is known _before_
the insert — which matters for building related rows inside one transaction.
PostgreSQL 18's native `uuidv7()` would remove that trade-off; revisit then.

**ULID / NanoID.** Same sortable-and-random properties, but stored as text. That
gives up the native `uuid` type's 16-byte storage and comparison speed for no
gain.

## Consequences

**Easier**

- Ids are safe to expose. There is no enumeration surface and no volume leak.
- Index locality close to a sequence, so write throughput does not degrade as
  tables grow.
- `ORDER BY id` is chronological, which is a free tiebreaker for feeds.
- Ids are available before insert, so a transaction can build a whole object
  graph without round trips.
- Merging data across environments cannot collide.

**Harder / accepted**

- 16 bytes per key versus 4 or 8. Measurable at very large scale; not the
  bottleneck here.
- Ids are ugly in logs and support conversations. Ticket keys cover the cases
  where humans need to name something.
- Creation time is inferable from an id. Acceptable — `createdAt` is returned in
  the API anyway.
- Rows inserted by raw SQL must supply their own id, since the default lives in
  the client rather than the database.
